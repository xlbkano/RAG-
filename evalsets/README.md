# 评测集

## 文件格式

JSONL，每行一条：

```json
{
  "qid": "q01",
  "query": "问题原文",
  "type": "single_hop | paraphrase | multihop | no_answer",
  "difficulty": "easy | medium | hard",
  "gold_blocks": ["<doc_id>:b12"],
  "partial_blocks": [],
  "gold_docs": ["kubernetes/xxx.md"]
}
```

`gold_blocks` 指向的是**与切分策略无关的评测块**（每篇文档固定 1024-token 网格），
不是某个策略的 chunk id。所以同一份标注可以同时评四种切分策略，这是横向对比成立的前提。
块 id 由 `doc_id`（语料相对路径的 sha1 前 12 位）+ 块序号组成，只要语料文件不改，id 就稳定。

## quick_v1.jsonl（当前使用）

50 条：44 条有答案 + 6 条无答案。题型覆盖单跳事实题与同义改写，难度 easy 20 / medium 26 / hard 4。

**标注方法**（刻意避开自己系统的排序）：

1. 先按主题挑出要出题的文档（K8s 概念/调度/存储、FastAPI 依赖注入/安全/流式等）；
2. 用**内容特征词**在原文里定位答案所在位置（`scripts/probe_block.py`），映射到评测块——
   这一步只做纯文本包含匹配，不经过检索器。若拿检索结果当 gold，系统召不回来的内容
   永远不会成为 gold，Recall 天然虚高；
3. 用**自己的话**重写问题，不抄原文；
4. 跑 4-gram 泄漏检测（`python tasks.py check-suite --suite ...`），query 的 4-gram
   原样出现在 gold 块里的比例超过 0.4 就改写。实测有 2 条超标，已重写。

## 这份集的局限（必须写进报告，不能只报数字）

| 局限 | 影响 | 后续 |
| --- | --- | --- |
| 单 gold | 一道题只标 1 个块，若其它块也能回答，该配置被误判为未召回 | 200 条版改为多 gold + 候选池复核 |
| 只有单跳题 | 测不出多跳/指代消解能力，`multihop` 类型空缺 | 200 条版补 40 条跨段多跳 |
| 单人标注 | 无一致性校验，无法报 Cohen's κ | 200 条版抽 20% 双人复核 |
| n=44 | 单组 Recall@5 的 95% 置信区间约 ±13pt，**几 pt 的差距没有解释力** | 报告里一律用成对 bootstrap 给差值区间 |

最后一行是这套集最容易被误用的地方。所以 `scripts/report.py` 里所有"某配置比某配置好多少"
的结论都带成对 bootstrap 的 95% 区间，区间跨 0 就标"不显著"，不给点估计下结论。

## 扩到 200 条的做法

1. 语料不变，按类型配额补：单跳 90 / 同义改写 40 / 跨段多跳 40 / 指代省略 20 / 无答案 10；
2. 多跳题的 gold 是**两个块**，两个都必须出现在 top-k 才算召回（`recall` 天然支持多 gold）；
3. 每条至少标 1 个 `partial_blocks`（部分相关），供 nDCG 用分级增益；
4. 抽 20% 由第二个人独立标，算 Cohen's κ，低于 0.70 的题重标或丢弃。

## 纪律

报告和简历里的每个指标，都要能通过 `results/{run_id}/config.json` 里的
`dataset.sha1` 追溯回某个具体版本的评测集文件。改了标注就换文件名（`quick_v2`），
不要原地改——否则历史 run 的数字会对不上当时的数据。
